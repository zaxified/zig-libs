## What an OPRF is

A two-party protocol computing `output = F(skS, input)` where the
server holds `skS`, the client holds `input`, and afterwards the server
has learned nothing about `input` (it only ever sees a randomly blinded
group element) and the client has learned nothing about `skS` beyond
the single PRF output. Building block for Privacy Pass, OPAQUE,
password-breach lookup (à la "Have I Been Pwned" k-anonymity
upgrades), private set membership, etc.

## Modes built

| Mode | Byte | Built | What it adds |
|------|------|-------|--------------|
| OPRF | 0x00 | yes | base protocol: `blind` → `blindEvaluate` → `finalize` |
| VOPRF | 0x01 | yes | server proves DLEQ `log_G(pkS) == log_blinded(evaluated)`; client verifies before unblinding |
| POPRF | 0x02 | yes | public `info` input tweaks the key: `t = skS + HashToScalar("Info"‖len‖info)`, evaluation is `t^-1 *`, proof is against the client-derivable `tweakedKey = G*m + pkS` with the composite lists **swapped** (the proven relation is `t*evaluated == blinded`) |

POPRF reuses the whole DLEQ engine and hash layer; only `poprfInfoScalar`, the tweak/inverse
arithmetic, and the `info` block in the Finalize hash are its own.

**API shape.** The ciphersuite is a comptime parameter: `Protocol(G)`
(`src/protocol.zig`) is the whole functional layer for a group backend `G`
(`src/groups.zig`, one namespace per suite with the same declarations:
widths, `hashToGroup`/`hashToScalar`, `encode`/`decode`, `mulSecret`/
`mulPublic`, scalar ops). `Suite(.p256_sha256)` or the named instance gives
the namespace; its functions have the top level's names and argument order,
only the widths (`Ne`, `Ns`, `Nh`, `wide_length`) differ. The top level of
`root.zig` is `Ristretto255Sha512` re-exported, so the single-suite top-level API
stays what it was.

**Batching** (what CIRCL's `Client.Blind(inputs)`/`Server.Evaluate` and
facebook/voprf's `batch_*` calls do): `blindEvaluateBatch` (OPRF, no
proof), `blindEvaluateVerifiableBatch` / `blindEvaluatePoprfBatch` (one
constant-size proof for the batch), `finalizeVerifiableBatch` /
`finalizePoprfBatch` (one proof check, then unblind + hash per element;
nothing written unless the proof verifies). Every batch call refuses an
empty batch or mismatched slice lengths with an error.

**Context objects** (facebook/voprf's `OprfClient`/`VoprfClient`/
`PoprfClient`/`OprfServer`/`VoprfServer`/`PoprfServer`, CIRCL's
`Client`/`Server`): per suite, thin state holders over the functions — the
client keeps its blind and blinded element (and POPRF's tweaked key)
between `blind` and `finalize`; the server keeps its key pair (`derive`
from a seed, `publicKey`, `blindEvaluate[Batch]`, `evaluate`). They add no
protocol logic and hold secrets by value, so the owner calls `wipe`.

**Hash-to-curve for the NIST suites** (`src/h2c.zig`): RFC 9380
`expand_message_xmd` over any SHA-2 hash and any `ell`, `hash_to_field`
(`m = 1`, `L` = 48/72/98: the two `L/2`-byte halves are each below the
modulus, so the reduction is one multiply and one add), the straight-line
simplified SWU (§6.6.2) with `sqrt_ratio` for `q = 3 mod 4` (Appendix
F.2.1.2), and `hash_to_curve` `_RO_` (`h_eff = 1`). Built only on the
siblings' public `Fe` API; no sibling was edited. Checked against every
`u[0]`/`u[1]`/`Q0`/`Q1`/`P` of RFC 9380 Appendix J.1.1/J.2.1/J.3.1 and
Appendix K.1/K.3.

## The DLEQ construction (RFC 9497 §2.2)

A batched, Fiat-Shamir-transformed Chaum-Pedersen proof that one scalar
`k` satisfies `B = k*A` and `D[i] = k*C[i]` for every element of two
equal-length lists — constant proof size (2 scalars, 64 bytes)
regardless of batch size. Exact transcript order (the part that MUST be
byte-exact — every length is I2OSP(len, 2) big-endian):

1. `seed = SHA-512( len(Bm)‖Bm ‖ len(seedDST)‖seedDST )`,
   `seedDST = "Seed-" || contextString`.
2. Per element `i`:
   `di = HashToScalar( len(seed)‖seed ‖ I2OSP(i,2) ‖ len(Ci)‖Ci ‖
   len(Di)‖Di ‖ "Composite" )`; composites `M = Σ di*C[i]` and
   `Z = k*M` (prover, `ComputeCompositesFast`) or `Z = Σ di*D[i]`
   (verifier, `ComputeComposites`).
3. Prover picks fresh random `r`, forms `t2 = r*A`, `t3 = r*M`;
   challenge `c = HashToScalar( len(Bm)‖Bm ‖ len(M)‖M ‖ len(Z)‖Z ‖
   len(t2)‖t2 ‖ len(t3)‖t3 ‖ "Challenge" )`; response
   `s = r - c*k (mod L)`. Proof = `(c, s)`.
4. Verifier recomputes `t2 = s*A + c*B`, `t3 = s*M + c*Z`, re-derives
   the challenge, and compares with `proof.c` (timing-safe here).

`HashToScalar` is the suite's `hash_to_field` into the scalar field
(ristretto255: `expand_message_xmd(SHA-512, msg, "HashToScalar-"‖
contextString, 64)` reduced little-endian; decaf448: XOF-SHAKE256, 64
bytes; NIST: XMD with the suite hash, `L` bytes, big-endian); `contextString
= "OPRFV1-" ‖ I2OSP(mode,1) ‖ "-" ‖ identifier` — so proofs are
domain-separated per mode and per suite. `I2OSP(len, 2)` prefixes use the
suite's `Ne`/`Nh`.

## Threat model

- **Malicious server (VOPRF/POPRF)**: may try to evaluate under a
  different key (e.g. to partition users). Countered by the DLEQ proof;
  `finalizeVerifiable`/`finalizePoprf` verify BEFORE unblinding and
  fail closed with `error.InvalidProof` (typed error, never a panic,
  no output on failure).
- **Curious server (all modes)**: sees only `blind * HashToGroup(input)`
  with a fresh uniformly random `blind` — information-theoretically
  independent of `input`.
- **Malicious client**: sees `skS * blindedElement` (+ ZK proof, which
  by zero-knowledge reveals nothing beyond validity). §7.2.3's static
  Diffie-Hellman/security-limit considerations (rotate keys before
  ~2^30-ish evaluations for tight bounds) are the application's
  responsibility.
- **Wire attacker**: all deserializers validate — `Element.fromBytes`
  enforces canonical ristretto255 decoding AND rejects the identity
  (§4.1 DeserializeElement); `deserializeScalar`/`Proof.fromBytes`
  enforce canonical scalars. Applications MUST deserialize received
  elements through these (per §3.3).
- **Side channels**: `skS`, the client `blind` (and its inverse), POPRF's
  `t`/`t_inv` and the DLEQ nonce `r` are multiplied by the sibling
  **`ct25519`**, not by `Ristretto255.mul`. std's `mul` is a constant-time
  4-bit-window ladder that then ends with `try q.rejectIdentity()`, a branch
  on a scalar-derived value, and the error union it returns forces a `catch`
  at every secret-scalar call site. `ct25519` is std's identical ladder with
  that tail removed: the neutral element is a value, there is no error union,
  and no call site can branch on the scalar. This is evidenced by a
  ctgrind-style valgrind/memcheck run, not by reading the source: the harness
  lives in `ct25519` (`scripts/checks/ctgrind.sh ct25519`), since it is
  `ct25519` that performs the multiply, and it carries a paired negative
  control that routes the same tainted scalar through std's
  `Ristretto255.mul` and reports the `rejectIdentity` branch. Mode, switch
  and counts are in `ct25519/SPEC.md` § "Constant-time check".

  **The other four suites.** decaf448's secret multiplies use
  the sibling's `Element.scalarMul`, which returns a value (no error union,
  its own ctgrind harness). The NIST suites use the siblings' constant-time
  `mulInto`, which ends with ONE laundered branch on the product's identity
  verdict (their ECDH shape); for a validated non-identity point that verdict
  is "the scalar is 0 mod n", voprf maps it to the identity element instead
  of an error, so no voprf API reports it. The NIST hash-to-curve treats the
  input as secret (it is the client's private input): `cMov` selects only,
  no branch on `u` or any field value — the sibling's `Fe.cMov`, which
  launders its mask (p256, p384, p521). Per-suite ctgrind rows: see
  the card's Hardening line and `scripts/checks/ctgrind-expected.tsv`.

  PUBLIC scalars stay on std's `mul` on purpose: `verifyProof`'s `s`/`c`
  are wire data, the composite `di` are hashes of wire elements, and
  POPRF's `m` is a hash of the public `info` — nothing there is secret,
  and the rejections are genuine fail-closed checks on peer input.

  The proof-challenge comparison uses `std.crypto.timing_safe.eql`. The
  `skS == 0` retry in `deriveKeyPair`, POPRF's `t == 0` check and
  `unblind`'s zero-blind check branch exactly where RFC 9497's own
  pseudocode branches; they are the only secret-dependent branches left,
  and each guards an operation that is undefined at zero rather than
  reporting the result of a multiplication.
- **Randomness**: this module has NO internal RNG. The `blind` scalar
  and the proof randomness `r` are caller-supplied (`scalarFromWideBytes`
  turns 64 CSPRNG bytes into a uniform scalar, §4.7.2). Reusing `r`
  across proofs, or a predictable `blind`, breaks the respective
  security property — that contract is on the caller, and is what makes
  the RFC's `ProofRandomScalar` KATs reproducible.

## Secret residue on the dead stack

Every public entry point that touches a secret (`scalarFromWideBytes`,
`deriveKeyPair`, `generateProof`, `blind`, `blindEvaluate`, `finalize`,
`evaluate`, `blindEvaluateVerifiable[Batch]`, `finalizeVerifiable`,
`blindPoprf`, `blindEvaluatePoprf[Batch]`, `finalizePoprf[Unverified]`,
`evaluatePoprf`) runs its body one frame down (`burn.run`) and then zeroes the
stack that body dirtied (`burn.zig`: 2 KiB for the reduction, 8 KiB for
`deriveKeyPair`, 20 KiB for the one-multiply calls, 28 KiB for the DLEQ
prover and everything that verifies or proves). Measured body depth
(when the sizes were chosen), ReleaseFast: 0.4 KiB (`scalarFromWideBytes`) .. 11.9 KiB
(`finalizeVerifiable`/`finalizePoprf`); the burns are about 2x that.
Secret inputs (`sk`, the blind, the proof nonce, the seed) are taken by
`*const`; secret outputs (the key pair, the finalize/evaluate output, the
reduced scalar) are returned through `out` — never by value, never inside an
error union (the public `Proof`, `Element` and `VerifiableEvaluation` values
are returned by value; they carry no secret).

`src/stackprobe_test.zig` paints the stack, calls each entry point and scans
the dead window for the seed, key, blind and its inverse, the unblinded
element, the PRF output, the DLEQ nonce, `c*k`, `t = sk + m`, `t^-1` and the
input; each set has a control needle that must be found. The other four
suites (decaf448, P-256, P-384, P-521, whose burns are scaled ×2,
`groups.zig` `burn_scale`) are probed at `deriveKeyPair`,
`scalarFromWideBytes`, `blind`, `blindEvaluate`, `finalize`, `evaluate`,
`blindEvaluateVerifiable` and `evaluatePoprf` for the byte images the API
handles (seed, key, blind, proof nonce, wide string, outputs, input); the
sibling curves' internal encodings (`blind^-1`, the unblinded element) are
not needles there. It runs only in ReleaseFast/ReleaseSmall (Debug fills
`undefined` with `0xaa`).

Not covered: the standalone helpers `hashToScalar`, `hashToGroup` and
`expandMessageXmd` (public, defined over transcripts; they only see a secret
when an entry point above calls them, inside its burned body); a secret the
caller keeps in its own frame (`KeyPair`, the blind) — that is the caller's to
erase; registers and the red zone below the stack pointer.

## Input bounds

RFC 9497 frames every `input` and `info` with a two-byte length, so both are
bounded at `max_input_length = 2^16 - 1` bytes. Every entry point that takes
one checks it first and returns `error.InputTooLong` (in `DeriveKeyPairError`,
`BlindError`, `FinalizeError`, `EvaluateError`, `FinalizeVerifiableError`,
`FinalizeBatchError`, `PoprfEvaluateError`, `PoprfDirectEvaluateError`, and
`poprfInfoScalar`'s own `InputTooLongError`); the bound is a checked error, never an assert
followed by an `@intCast`, which would be a panic in safe builds and UB in ReleaseFast for a slice a
caller can pass. Test: `suite_kat_test.zig` "2^16-1
input bound" (65536 refused, 65535 accepted, every entry point, two suites).

## Performance

`zig build bench-voprf` (`tools/bench.zig`, ReleaseFast) against CIRCL's `oprf` (`tools/go_bench`); batch 1,
POPRF blind and finalize counted as their sum, because RFC 9497 and this module derive the tweaked key
in `Blind` while CIRCL defers it to `Finalize`. Before timing, per suite × mode, both sides are
cross-checked: the same `DeriveKeyPair` key, byte-equal FullEvaluate outputs and blinded elements (same
blind scalar), our server's evaluation and proof finalized by CIRCL, CIRCL's finalized by us. The
current figures, with their date, are the card's `**Performance:**` line; they are not repeated here.

## What is deliberately not done

- **`GenerateKeyPair`/`RandomScalar` with an internal RNG** (§3.2/§2.1)
  — no-RNG module policy; `deriveKeyPair` + caller-supplied randomness
  cover both KATs and production use.
- **Serialization frameworks** (facebook/voprf's serde derives) — the wire
  values are the RFC's fixed-width byte strings (`toBytes`/`fromBytes`).
- **Moving the NIST hash-to-curve maps into `p256`/`p384`/`p521`.** This
  module owns RFC 9380's P-256/P-384/P-521 `_XMD_SSWU_RO_` suites
  (`h2c.zig`, the RFC's J.1.1/J.2.1/J.3.1 vectors) for its own ciphersuites;
  the curve modules point here and offer no hash-to-curve API of their own
  (their reference, OpenSSL, has none). `expand_message_xmd` is the shared
  `sha2.expandMessageXmd`.
- **A shared `expand_message_xof`.** `h2c.expandMessageXof` (parts,
  SHAKE256), `bls12_381`'s and `decaf448`'s are three ten-line wrappers over
  std's `Shake256` with different call shapes (parts / one message / a
  runtime-length output); there is no SHAKE module to host one, and a module
  for ten lines would cost more than the copies.

## Backlog / deferred

- *BOUNCED (quiet-host):* **Performance leftovers** (every counted row of the card's Performance line is <= 0.86x CIRCL):
  `powC1` in `sqrt_ratio` is a plain square-and-multiply (an addition chain
  would cut it), and the composite sums use one `mulPublic` per term instead
  of a multi-scalar multiply. "fastest" is unmeasured: facebook/voprf (Rust)
  would be the second implementation. Both are micro-optimisations (an addition chain for `powC1`, a multi-scalar multiply for the composite sums) whose effect on a row already at 0.18-0.86x the reference needs a quiet-machine A/B; the "fastest" figure needs facebook/voprf's API driven through a Rust harness with the same interop pre-checks as `tools/bench.zig`.
