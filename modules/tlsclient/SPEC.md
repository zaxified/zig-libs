## What this module is, and what it is not

A copy of Zig 0.16.0's `std.crypto.tls.Client` whose handling of the
server's Certificate message is replaced: std parses each certificate bare
and verifies it link by link against the next (issuer name, validity,
signature), stopping at the first one the bundle vouches for. That walk
never reads basicConstraints (ziglang/zig #35877, open since 2026-06-21), so
a leaf signed by another leaf is accepted -- anyone with one certificate can
impersonate any host. Here:

1. every certificate is proven well-formed by `x509.safe.validateCertificate`
   before `std.crypto.Certificate.parse` sees it (std's DER element parser
   reads out of bounds on malformed input -- `x509` SPEC, `safe.zig`);
2. the leaf is parsed for the hostname check (std's `verifyHostName`,
   unchanged) and the CertificateVerify key, as before;
3. the whole chain goes to `x509.verifyChain` with the bundle's certificates
   for every issuer name the chain mentions as trust anchors, and
   `required_eku = .server_auth` (`verify.zig`).

**Defaults are Go's `crypto/tls` client's** (owner, 2026-10-13; until then
"no change to std's behaviour by default"). The ClientHello is built at run
time (`hello.zig`): Go's groups (X25519MLKEM768, X25519, P-256, P-384, P-521)
with shares for the first two, the rest reached by HelloRetryRequest. std's
shape stays reachable -- `groups = key_share_groups = std_groups` -- and a test
pins that hello to std's byte for byte, except the three TLS 1.2 ECDHE_ECDSA
suites this module adds. A CertificateRequest without `client_auth` still
fails as in std. A consumer still changes one import. The additions, each
marked `zig-libs tlsclient` in `Client.zig`:

- **Version bounds** `min_version`/`max_version` (Go `MinVersion`/`MaxVersion`).
- **Groups** `groups` (Go `CurvePreferences`) and `key_share_groups`; key pairs
  are generated only for a share offered or a group a server picks. P-521
  (std has none) through the `p521` module.
- **HelloRetryRequest** (RFC 8446 §4.1.4): selected group and/or cookie,
  message_hash transcript, second ClientHello on record version 0x0303; a
  second HRR, an HRR that changes nothing, names a group we shared or never
  listed, or is not TLS 1.3 is refused. TLS 1.3 now switches to the handshake
  cipher right after ServerHello and ignores the compatibility
  ChangeCipherSpec (std waited for one).
- **TLS 1.2 ECDHE_ECDSA suites** (AES-GCM, ChaCha20); the suite must match the
  certificate's key type.
- **Ed25519 server certificates** (TLS 1.3 CertificateVerify, TLS 1.2
  ECDHE_ECDSA): std carried the verifier but its scheme→key mapping never
  reached it.
- **Session view** `Options.connection_info` → `ConnectionInfo` (Go
  `ConnectionState`): version, suite, group, ALPN, HRR, EMS, the peer's
  certificates as sent, the stapled OCSP response and SCTs, all copied into
  caller storage (`ConnectionInfoTooSmall` rather than truncation). Also
  `Client.cipher_suite`, `negotiated_group`, `hello_retry_request`.
- **OCSP / SCT requests** on by default as in Go (`request_ocsp`,
  `request_scts`); neither is verified (Go verifies neither). TLS 1.3: from
  the leaf's CertificateEntry; TLS 1.2: SCTs from ServerHello, OCSP from the
  CertificateStatus message (only after the server promised it).
- **Verification hook** `verify_connection` (Go `VerifyConnection` /
  `VerifyPeerCertificate`): runs once the server is authenticated, before our
  Finished; an error is `TlsConnectionRejected`.
- **TLS 1.2 extended master secret** (RFC 7627) and empty
  renegotiation_info (RFC 5746), offered by default as in Go.
- **Keying-material exporter** `exportKeyingMaterial(label, context, out)`:
  RFC 8446 §7.5; TLS 1.2 RFC 5705 only with EMS and without the PRF's own
  labels (Go's rules). Equal to `openssl s_server -keymatexport` in both.
- **Client authentication, Go's reach** (S2 R6): RSA client keys
  (`PrivateKey.rsa`, the `rsa` module's pair; TLS 1.3 RSA-PSS, TLS 1.2
  PKCS#1 v1.5 or PSS), the scheme chosen from the server's list in its order
  (TLS 1.2 schemes name only the hash, so a P-256 key may sign ECDSA+SHA384
  there), `client_auth_select` (Go `GetClientCertificate`) called with the
  request's schemes and CA names, and **TLS 1.2 client certificates** (RFC
  5246 §7.4.4-7.4.8: Certificate before ClientKeyExchange, CertificateVerify
  over SHA-256/384/512 running hashes of the messages, kept only when client
  auth is configured). Ed25519 client keys stay TLS 1.3 only: PureEdDSA
  cannot sign the TLS 1.2 messages' hash (an empty Certificate is sent).
- **TLS 1.3 session resumption** (Go `ClientSessionCache`, opt-in as there):
  `Options.session_cache` → `SessionCache` over caller-owned `ClientSession`
  entries (one per server name, oldest replaced; optional `std.Io.Mutex`).
  A full handshake reserves the entry with the resumption master secret and
  the server's chain; NewSessionTickets (std dropped them) fill in the
  ticket and its PSK; the next connection offers it (psk_dhe_ke -- a fresh
  ECDHE still runs; no 0-RTT) with the binder over the truncated hello,
  re-bound after an HRR or dropped when the HRR's suite hash differs. A
  resumed session skips Certificate/CertificateVerify, shows the kept chain
  in `ConnectionInfo` (`did_resume`) and still runs `verify_connection`.
  Not offered past the ticket lifetime (≤ 7 days) or the leaf's notAfter.
  PSK derivation, binder and the NewSessionTicket codec are `tlsresume`'s.
  TLS 1.2 session tickets (RFC 5077) are not resumed.
- **Host names as Go checks them** (`x509.hostname`, RFC 9525): SAN only --
  std fell back to the subject's commonName -- and an IP-literal host
  (`127.0.0.1`, `[::1]`) is matched against iPAddress SANs and sent without
  SNI (RFC 6066 §3 forbids an address there; std sent it and could not match
  an IP at all).
- **std defects fixed on the way** (all remotely triggerable by a server,
  found by `TLSCLIENT_FUZZ` 2026-10-13, regression tests in place): a
  ServerHello session-id echo of 253..255 bytes overflowed a `u8` sum; a TLS
  1.3 record shorter than the AEAD tag and a TLS 1.2 record shorter than IV +
  MAC underflowed their length; an all-zero TLS 1.3 plaintext (no content
  type) indexed `msg[-1]` after the handshake and underflowed the fragment
  end during it (RFC 8446 §5.4: unexpected_message); `tls_version` was read
  undefined by handlers of messages arriving before the ServerHello.
- **KeyUpdate sent** (RFC 8446 §4.6.3): a server's update_requested is
  answered with our KeyUpdate before our next record, and the client updates
  on its own after `key_update_after` (2^23) records. std switched its write
  key on update_requested without telling the server, so the next record was
  refused (bad_record_mac; reproduced with `s_server`'s `K`).

- **ALPN (RFC 7301).** `Options.alpn_protocols` (default empty: no
  extension) and `Client.alpn_protocol`. The extension goes last in the
  ClientHello (after server_name, appended as one more iovec and transcript
  update); the record, handshake and extensions lengths grow by its size
  (`hello_header` patch). The answer is read from EncryptedExtensions (TLS
  1.3, `encryptedExtensionsAlpn`) or ServerHello (TLS 1.2): exactly one
  name, one we offered, the extension once -- else `TlsIllegalParameter`. A
  server's no_application_protocol alert surfaces as `TlsAlert`. With
  nothing offered a server's ALPN is ignored, as std ignores it.
- **Client certificates, TLS 1.3 (RFC 8446 §4.3.2, §4.4.2-4.4.3).**
  `Options.client_auth` (default null: a CertificateRequest stays std's
  `TlsUnexpectedMessage`; TLS 1.2 requests always do). `parseCertRequest`
  keeps the context and whether `signature_algorithms` (mandatory, once)
  lists our scheme. Before the client Finished: a Certificate echoing the
  context with the chain (no entry extensions) and a CertificateVerify signed
  over 64 spaces, "TLS 1.3, client CertificateVerify", 0x00 and the
  transcript hash through our Certificate; ECDSA (RFC 6979, DER) or Ed25519.
  **When the request does not list our scheme we send an empty Certificate
  and no CertificateVerify** -- RFC 8446 §4.4.2.3's rule for "no suitable
  certificate"; the server then decides (`-verify` proceeds, `-Verify`
  aborts with certificate_required, seen on our first read). Failing locally
  instead would refuse servers that ask optionally. The application secrets
  stay on the transcript through the server Finished; the client Finished
  covers our two messages. All three go out as TLS 1.3 records under the
  client handshake key, sequence 0, 1, … (`writeHandshakeRecords`, split at
  2^14 - 1 bytes). `ClientAuth.key` is a pointer (borrowed for the
  connection, so `Options` copies never carry the key); the signature runs
  one frame down and the stack it dirtied is zeroed (`burn.zig`) — std's
  signers leave the key and the nonce in their own frames, which the
  `secureZero` of our locals never reached. `stackprobe_test.zig`
  (ReleaseFast) checks all three key types for 0 residue.
  `max_client_auth_len` (16 KiB) bounds our messages.

**Not here, on purpose:** revocation (OCSP/CRL), certificate transparency --
std has neither, and adding them is not this module's job. `.ca =
.self_signed` and `.no_verification` behave as in std.

## Limits and refusals

- **At most 10 certificates** in a server's Certificate message
  (`verify.max_chain_len`): real chains are 2-4; `x509.Options.max_intermediates`
  is 8. More is `error.TlsCertificateNotVerified`.
- **A certificate over `x509.safe.max_certificate_len` (8 KiB)** is refused.
- **An empty Certificate message** is refused at once (std failed on the
  next message instead).
- `verifyChain` runs in a 16 KiB stack `FixedBufferAllocator`; running out is
  a refusal, never a partial verification.

## Key shares (2026-10-11; P-384 on `p384` since 2026-10-13)

std's ClientHello — kept byte for byte, an offline test proves it — offers
X25519MLKEM768, secp256r1, secp384r1 and X25519 shares, so all four key pairs
are generated per handshake. std computes the P-256 and P-384 public keys
with `basePoint.mul` (a 4-bit window, 64 or 96 doublings), which was ~2/3 of
the client's CPU. `keygen.zig` produces the same key pairs, byte for byte
(differential tests against std's `generateDeterministic`): the secret scalar
by std's own derivation (copied — `p384`'s `generateDeterministic` orders the
HMAC-DRBG input differently and would change the ClientHello), the public
point by a constant-time fixed-base comb: `p256.P256.combMulBase` for P-256,
`p384`'s `KeyPair.fromSecretKey` for P-384. The ECDHE step on secp384r1 is
`p384.ecdhInto`; the client's P-384 CertificateVerify signature is `p384`'s
(RFC 6979 nonces, so its bytes differ from std's — openssl `-Verify` accepts
it in the interop test); the server's P-384 signature is decoded by std and
verified by `p384`, as P-256 is by `p256`.

2026-10-11..13 history: a P-384 comb over std's field lived in this file with
a generated table and a copy of std's `addMixed` minus its closing
`cMov(p, q.x.isZero())` (ctgrind saw that select as secret-dependent loads);
the `p384` module took over its numbers and its ctgrind lesson. ctgrind row
`tlsclient/kex` covers `keygen.zig`. Negative controls: 8 mutants over the
comb and the derivation (2026-10-11), all killed; the P-384 server-signature
test goes red when `p384`'s verify is skipped (2026-10-13).

## Anchoring

- **External anchor:** `interop_test.zig` drives the handshake against
  `openssl s_server` (skipped when `openssl` is absent) with openssl-made
  chains (`src/testdata/`, recipe in its README): the honest chain verifies,
  the forged chain (leaf signed by another leaf's key -- OpenSSL's own
  `verify` refuses it with "invalid CA certificate") is refused, and std's
  client still accepts it. The verification decision itself is `x509`'s,
  anchored in that module.
- A mutant that drops the `verifyAgainstBundle` call turns the forged-chain
  interop test red (checked 2026-09-25).
- **2026-10-04 additions.** Against `openssl s_server` (loopback, throwaway
  fixtures, `-rev` echo): ALPN -- openssl picks `h2` from our `http/1.1,h2`
  (its own order), refuses a list with nothing in common with
  no_application_protocol, and a server without ALPN leaves
