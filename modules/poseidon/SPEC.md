# poseidon — design, sources & divergences (SPEC)

Auditor/design reference. Consumer usage lives in `README.md`; metadata lives
in `src/root.zig`'s `pub const meta`; this file does not restate either.

## What the hard part actually is

The permutation is twenty lines. Everything that decides *which numbers go in*
is the work, and it is where implementations diverge:

| decision | where it comes from here |
|---|---|
| round constants | `src/grain.zig`, ported from the authors' Grain-LFSR sage script |
| MDS matrix + its generation rule | same script's `create_mds_p` (Cauchy matrix) |
| `R_F` / `R_P` per field and width | `N_ROUNDS_P` / `N_ROUNDS_F`, copied from circomlib with its own provenance comment |
| S-box exponent `alpha` | fixed at 5; see below |

### `alpha = 5`, not 3

`x -> x^alpha` must be a bijection on `GF(p)`, i.e. `gcd(alpha, p-1) = 1`. For
both fields here `3 | p-1`, so `x^3` is not a bijection and `alpha = 5` is the
smallest admissible odd exponent. Both shipped parameter sets are `x^5`, and
every published vector is `x^5`. `x^-1` (the "Starkad/Poseidon over binary
fields" branch of the reference script) and `alpha = 3` are out of scope; the
Grain seed encodes the S-box choice, so adding one is a new parameter set with
new constants, not a flag.

## Sources

Primary, in the order they were consulted:

1. **The paper** — *Poseidon: A New Hash Function for Zero-Knowledge Proof
   Systems*, Grassi/Khovratovich/Rechberger/Roy/Schofnegger,
   <https://eprint.iacr.org/2019/458>. Defines the HADES design strategy and
   the round-number analysis, but does **not** publish usable constants.
2. **The authors' reference code** — `hadeshash`,
   <https://extgit.iaik.tugraz.at/krypto/hadeshash> (redirects to
   `extgit.isec.tugraz.at`). `code/generate_parameters_grain.sage` is the
   constant generator this module ports; `code/poseidonperm_x5_25{4,5}_{3,5}.sage`
   are complete reference permutations with their constants inline;
   `code/test_vectors.txt` is the published KAT set.
3. **The deployed implementation** — `iden3/circomlib`
   (`circuits/poseidon.circom`, `circuits/poseidon_constants.circom`,
   and their `_old` counterparts) and `iden3/circomlibjs`
   (`src/poseidon_reference.js`, `src/poseidon_opt.js`,
   `src/poseidon_constants.json`, `test/poseidon.js`).

The paper and the deployed implementation **do not conflict on the function**.
They conflict on nothing that changes a digest, which was the thing worth
checking. The divergences that do exist are below.

## Divergences

### 1. Reference form vs optimized form — followed: reference, byte-compatible with both

circomlib ships Poseidon twice:

* `poseidon_old.circom` + `poseidon_constants_old.circom` — the plain HADES
  round structure, full round-constant table (195 values at `t = 3`), MDS used
  as `out[i] = Σ_j M[i][j]·in[j]`.
* `poseidon.circom` + `poseidon_constants.circom` — the *optimized* form
  (constant folding + sparse matrix factorisation): the round-constant table
  is folded down to `t·R_F + R_P` values (81 at `t = 3`), a pre-matrix `P` and
  `R_P` sparse matrices `S` replace most of the partial-round work, and the
  stored `M` is the **transpose**, consumed as `out[i] = Σ_j M[j][i]·in[j]`.

Verified in hand rather than assumed: `poseidon_constants_opt.json`'s `M[1]`
is exactly the transpose of `poseidon_constants.json`'s `M[1]`, and its `C[1]`
has 81 entries against the reference's 195.

**This module implements the reference form.** It is the one the paper
describes, the one the authors' sage scripts publish, and the one that can be
read. The optimized form is an arithmetic reorganisation for constraint count,
not a different function: circomlibjs' own test suite asserts
`poseidon_opt == poseidon_reference == poseidon_wasm` on every vector, and
`src/vectors_test.zig` independently matches values taken from *both* JS
implementations. If this module ever grows a circuit backend, the optimized
form is what it should emit — and the reference form is what would check it.

Nothing here is Poseidon2 (Grassi/Khovratovich/Schofnegger 2023), which is a
genuinely different permutation with a different linear layer. Out of scope.

### 2. `R_P` rounded up to a multiple of `t` — followed: circomlib

circomlib's own comment, in both `poseidon.circom` and
`poseidon_reference.js`:

> Using recommended parameters from whitepaper
> <https://eprint.iacr.org/2019/458.pdf> (table 2, table 8) / Generated by
> …/calc_round_numbers.py / **And rounded up to nearest integer that divides
> by t**

That last step is circomlib's, not the paper's. It only ever *adds* rounds, so
it is conservative — but it changes the Grain seed (`R_P` is one of the seeded
fields), so it changes every constant. Every value in `N_ROUNDS_P` is
divisible by its `t`; `constants_test.zig` asserts that, because it is the
fingerprint of this decision. Following the paper's unrounded table instead
would produce a hash no deployed circuit could verify.

### 3. Which state element the partial round's S-box hits — followed: `state[0]`

The reference sage permutations apply `state[0] = state[0]^5` in the partial
rounds, and circomlib does the same. Other ecosystems have used the last
element. This is not a matter of taste: it is a different permutation. Both
choices produce a deterministic hash that round-trips perfectly, which is
exactly why the published vectors are the only thing that settles it — see
"Mutation" below, where this was broken deliberately.

## Parameter generation, and the one thing not reproduced

`grain.zig` is a faithful port of the sage script's GF(p) path, including the
two details that silently change the output:

* round constants are **rejection-sampled** (`while v >= p: redraw`), MDS seeds
  are **reduced** (`F(grain_random_bits(n))`). Using one rule for both
  desynchronises the stream.
* the Grain output filter consumes several clocks per emitted bit; it is not
  "one clock, one bit".

### The MDS rejection loop — reproduced

`mds_security.zig` carries the script's `algorithm_1`/`2`/`3` and
`check_minpoly_condition`, the subspace-trail tests of
Grassi-Rechberger-Schofnegger (<https://eprint.iacr.org/2020/500>), and
`derive` carries `generate_matrix`'s rejection loop around them.

Why it has to be there at all: a rejection is **not** a no-op. It consumes
another `2t` Grain draws, so every later value shifts. A generator without the
checks is silently wrong for any `(n, t, R_F, R_P)` where upstream happened to
reject a candidate — and it cannot tell you which parameter sets those are.
Adding them removes the boundary this file used to record ("cannot be pointed
at a new parameter set without running sage alongside").

For every parameter set shipped here the first candidate is the accepted one,
so **not one shipped table changed**. That is no longer prose: a
`constants_test.zig` case asserts `mds_candidates == 1` for all 18 of them,
alongside the digests that pin the values themselves.

#### How rare a rejection is, measured

`algorithm_3` rejects only when some ratio `λ_i/λ_j` of eigenvalues is a root
of unity of order at most `4t`. There are fewer than `(4t)^2` such roots and
`t(t-1)` ratios, so over a 254-bit prime the probability is about `2^-236`;
`algorithm_1` and `algorithm_2` need a rank-deficient `t x t` matrix, about
`1/p`. Empirically: a sweep of **816 BN254 parameter sets** (`t = 2..17`,
`R_P = 40..90`, `R_F = 8`) produced **zero** rejections.

That is a fine property for Poseidon and a bad one for a test suite — a check
that never fires is indistinguishable from `return true`. So the rejection
path is exercised over a small prime instead (`small_field.zig`,
`rejection_test.zig`). Over `p = 101`: 13 of 104 random matrices are rejected
and 5 of 48 `(t, R_P)` sets need more than one MDS candidate — enough that the
loop, its Grain-stream advance and `algorithm_1`'s sub-codes all get real
coverage.

## Anchoring

**Anchor grade:** class B · oracle EXTERNAL

- **Class B** — published cryptographic or algorithmic construction with published vectors.
- **Oracle EXTERNAL** — published vectors, goldens captured from a foreign implementation, or a test run against a live foreign peer.

**What the tests actually contain.** circomlibjs JSON consts byte-identical (constants_test.zig)

Grade 1 (published vectors / reference-implementation output) throughout —
this repo's strongest tier. Three upstream sources, each with the exact
retrieval command recorded in `src/vectors_test.zig` and
`src/constants_test.zig`:

| what | source | covers |
|---|---|---|
| permutation KATs | `hadeshash/code/test_vectors.txt` | BN254 `t = 3, 5`; BLS12-381 `t = 3, 5` — all `t` output words |
| hash-framing KATs | `circomlibjs/test/poseidon.js` | `Poseidon(1/2/4/6/16)`, non-zero initial state, multi-output |
| width sweep | circomlibjs *executed* (`poseidon_reference.js` and `poseidon_opt.js`, required to agree) | every `t = 2..17`, plus inputs at `r-1` |
| constants | `circomlibjs/src/poseidon_constants.json`; `hadeshash/code/poseidonperm_x5_25{4,5}_3.sage` | SHA-256 pins for all 18 shipped tables + literal spot values |

A **grade-2** cross-check also happened during development — an independent
Python port of the generator and the permutation, which reproduced every value
above — but it descends from the same sage script, so it is recorded as
corroboration and is not what the tests rest on. No grade-3 self round-trip is
used as an anchor anywhere.

#### The MDS security checks are grade 2 only, and here is why

There is no grade-1 anchor available for `algorithm_1`/`2`/`3`. The strongest
possible one would be a *published* parameter set whose accepted matrix is not
the first candidate: reproducing it byte-for-byte would prove both that the
checks fire and that ours fire in the same place. **No such set exists to
find.** Every published Poseidon-1 table generated by `create_mds_p` lives
over a 254/255-bit prime, where the rejection probability is `~2^-236` (see
above) — the 816-set sweep confirms it empirically for the whole circomlib
parameter space. Searched: circomlib/circomlibjs (`t = 2..17`, BN254),
`hadeshash`'s own `poseidonperm_x5_25{4,5}_{3,5}` sage files, and the
small-field ecosystems (Goldilocks/BabyBear in HorizenLabs' `poseidon2`,
Penumbra's `poseidon377`, Filecoin's `neptune`). The small-field ones do not
use `create_mds_p` at all — Poseidon2 builds its linear layer from
`generate_matrix_full`/`generate_matrix_partial`, and Penumbra states plainly
that it generates the Cauchy vectors *deterministically* (`x = 0..t-1`,
`y = t..2t-1`) rather than sampling, so no rejection loop runs there either.

What stands in its place, and what it is worth:

| evidence | what it does prove | what it does NOT |
|---|---|---|
| `constants_test.zig` — 18 shipped tables byte-identical to circomlib / the authors' sage, plus `mds_candidates == 1` | adding the checks changed nothing that is externally pinned | that a *rejection* is handled correctly — none occurs |
| `reference_interop.zig` — an independent sympy port of the four algorithms, fed matrices over `GF(101)`/`GF(251)` where rejections are common (19 of 168), compared on the verdict, the **sub-code** and the failing round | transcription fidelity, on inputs that actually fail | anything about a *shared misreading* of the sage source: both ports are ours |
| `rejection_test.zig` — `derive` over `GF(101)`, accepted matrix is the k-th draw and differs from the first | the loop advances the Grain stream, which is the failure mode that looks correct | — |
| the equivalence tests in `mds_security.zig` — fast path vs the literal transcription | the two `O(t^3)` rewrites (see that file) are not doing something else | — |

The sympy oracle is **not** external validation and is not described as such
anywhere. It is a second transcription of the same text by the same author; it
catches an index slip and it cannot catch a misread specification. sage is not
installed on the development host and installing it was out of scope.

### Mutation — evidence the tests bite

Poseidon's specific trap is that a wrong permutation is still a perfectly good
deterministic function. Eight mutations were introduced and reverted (restore
from a pristine copy, never `git checkout`).

**Four on the MDS security checks and the rejection loop:**

| mutation | result |
|---|---|
| `algorithm_1` tests `M^(i+1)` where the reference tests `M^i` | **caught** — the constructed sub-code batch in `reference_interop.zig` |
| `algorithm_1`'s sub-codes 2 and 3 swapped | **caught** — the code-2 unit test and the oracle's sub-code comparison |
| `IS` accumulates the whole eigenspace instead of `S_i ∩ E_λ` | **caught** — 6 tests, incl. fast-vs-literal agreement and every random-matrix oracle batch |
| `algorithm_3`'s divisor reduction inverted (`r` in `[2, 2t]` instead of `(2t, 4t]`) | **caught** — 4 tests, incl. `rejection_test` and the oracle |
| `check_minpoly_condition` drops the irreducibility half, keeping the degree check | **caught** — its unit test and 3 oracle batches |
| `derive` runs the checks and discards the verdict (the pre-existing omission) | **caught** — `rejection_test`: the accepted matrix equals the first candidate |
| **a rejection does not consume its Grain draw** (LFSR state restored on reject) | **caught** — `rejection_test` ×3 plus the oracle; the loop exhausts instead of converging |
| `algorithm_1`'s fast path walks `M^k e_0` (Krylov) instead of `e_0^T M^k` (observability) | **caught** — a dedicated unit test built to separate the two, plus the oracle |

The seventh is the one worth keeping: a rejection that fails to advance the bit
stream still yields a valid-looking, invertible, MDS, perfectly deterministic
matrix. No structural property notices. Only "the accepted matrix is the k-th
draw *and differs from the first*" does — which is why `rejection_test.zig`
replays `create_mds_p` by hand instead of trusting `derive`'s own output.

**Four earlier ones on the permutation and the generator** (restore verified by
file checksum — the module was untracked at the time, so `git diff` had nothing
to compare against):

1. **Partial-round S-box on the last element** instead of `state[0]`
   (`state[t-1] = sbox(state[t-1])`).
2. **Full S-box in the partial rounds** — applied to every element, i.e. the
   partial/full distinction dropped.
3. **Round split shifted** — `R_F/2 + 1` leading full rounds and one fewer
   partial round, keeping the total round count *and* the constant consumption
   identical.
4. **Generator**: MDS seed draws rejection-sampled instead of reduced
   (`grain.zig`, subtlety 1 inverted).

All four left the module compiling, all structural properties (invertible MDS,
injectivity, determinism, framing consistency) intact, and all four were caught.
The per-mutation results are tabulated in `README.md`. Two findings worth
keeping: the constant pins isolated mutation 4 to the *generator* and named the
layer, and mutation 4 was invisible to the `t = 5` vectors — no draw happened to
land above `p` there — so only the `t = 2..17` sweep caught it at that width.

## Constant time

**Yes for the permutation, and it is meant to stay that way.**

`permute` has fixed loop bounds, no data-dependent branches, and no
memory access indexed by a data value. Every field operation comes from the
sibling `bn254`/`bls12_381` `Fr`, which is `std.crypto.ff`-backed constant-time
Montgomery arithmetic. `sbox` is `square/square/mul` — no exponentiation ladder,
no `pow`.

**Does it matter?** For the intended use, usually not: hashing public circuit
data leaks nothing. It does matter in three cases this module is expected to
serve, so the property is worth having rather than disclaiming:

* Merkle *membership* proofs, where the leaf and the path are the secret;
* commitments to witness values;
* Fiat-Shamir transcripts absorbing secret intermediates.

**Caveats, stated rather than left open:**

* `Perm(t).init()` — the Grain derivation — is emphatically *not* constant
  time (rejection sampling, a duplicate-scan loop, a variable-length modular
  inversion, and now `mds_security`/`linalg`, whose control flow depends on
  ranks, polynomial degrees and factorisations). It consumes only public
  parameters, so this is fine, but do not reach for `grain.derive` or anything
  in `linalg.zig` with a secret.
* Unlike `k256` and `montint`, this module has **not** been CT-verified in the
  disassembly. The claim rests on the source shape plus `std.crypto.ff`'s own
  guarantees.

## Scope

### Not implemented, deliberately

* **Variable-length (sponge) hashing.** Poseidon's deployed use is
  fixed-arity: `Poseidon(n)` for a known `n`, which is what a circuit compiles
  to. A general sponge needs a padding rule and a domain-separation tag, and
  the deployed ecosystems do not agree on either (circomlib has none;
  Filecoin's `neptune` uses its own domain tags; other stacks use others).
  Adding one would mean shipping an unanchorable construction next to a set of
  byte-exact ones. If a caller needs it, `hashN` exposes the full permutation
  output, which is the primitive a duplex/sponge would be built from — but the
  convention should come from whatever it must interoperate with.
* **Poseidon2.** A different permutation (different linear layer), not an
  optimisation. Would be its own parameter set and its own vectors.
* **Circuit / constraint-system integration.** Out of scope here; the
  optimized round structure (divergence 1) is the thing a future `groth16`
  gadget would want.
* **Anything below `t = 2` or above `t = 17`** on BN254, and anything other
  than `t = 3, 5` on BLS12-381 — no published parameters, therefore no anchor.
  Note this is now a *policy* limit, not a capability one: with the rejection
  loop in place `grain.derive` reproduces upstream for any `(n, t, R_F, R_P)`
  without a sage run alongside. `mds_security.max_state_width` (17) is the only
  hard ceiling, and raising it costs compile time and stack, nothing else.
* **The GF(2^n) / `x^-1` branch** of the reference script, and
  `generate_matrix_full` / `generate_matrix_partial` — those build Poseidon2's
  linear layer, which this module does not implement. `check_minpoly_condition`
  is ported anyway (it is one of the four checks and the natural companion to
  the other three) but it is not on the MDS generation path, exactly as
  upstream.

### Why BLS12-381 stops at `t = 3` and `t = 5`

Upstream publishes reference scripts *and* test vectors for exactly those two
widths over this field. There is no published `R_P` table for other widths and
no deployed BLS12-381 Poseidon this could be byte-compatible with, so any
other width would be an unanchored guess wearing the name of an anchored
construction. `Perm(t)` is a `@compileError` for anything else.

Note also that only the **permutation** is externally anchored on this field.
The `hash`/`compress` framing (`[0] ++ inputs`, first output element) is this
module's own, borrowed from the BN254 side; it does not match Filecoin's
`neptune` or dusk, which use domain tags. `bls12_381_poseidon.zig` says so at
the call site.

### Follow-up, now BUILT: Rescue-Prime Optimized (`modules/rescue/`)

The obvious sibling. Same motivation (cheap in a circuit), same field, but a
different design strategy — every round is full, with alternating `x^alpha`
and `x^(1/alpha)` S-box layers, so it trades a much more expensive plain
evaluation for a lower algebraic degree. Rescue-Prime has a published
specification and KATs, so it would be anchorable at the same grade. It would
be a separate module, not a mode of this one: different round function,
different parameter generator, nothing shared but the field.

**Built as `modules/rescue/` — and two of the expectations above were wrong.**
It is a separate module as predicted, but it shares no field with this one:
the deployed variant (RPO) uses Goldilocks `p = 2^64 − 2^32 + 1`, which this
collection did not have, so `rescue` carries its own small field. And
"Rescue-Prime has published KATs" is false — the Rescue-Prime reference
implementation publishes none; RPO publishes 38. Anchoring, not deployment,
is what decided the variant.

## Performance note

`Perm(t).init()` runs the Grain LFSR once and then the MDS security checks.
The checks dominate: ~70 000 field multiplications at `t = 17`, which is 70 ms
at ReleaseSafe and 850 ms in Debug (`std.crypto.ff`'s constant-time multiply
costs 0.8 µs optimized and 9.6 µs unoptimized — measured, not assumed). At
`t = 3`, the case a Merkle tree actually builds, it is ~2 ms / 30 ms.

The whole test suite — which builds every `t = 2..17` instance three times
over — is ~3 s at ReleaseSafe/ReleaseFast and ~42 s in the default Debug lane,
against 0.45 s / 6 s before the checks existed.

**`heavy` was measured and rejected**, twice. Marking the module `heavy` runs
it at ReleaseSafe in the Debug lane, which does cut the run to ~3 s — but the
ReleaseSafe compile is 53 s against Debug's ~1 s, so the round trip goes 42 s →
56 s. Nothing depends on `poseidon`, so there is no second consumer to amortise
that compile over. Note this is *not* the usual heavy trade-off: the sibling
`bn254`/`bls12_381` are already `heavy`, and it does not help, because
`std.crypto.ff`'s generic code is instantiated in whichever module calls it.

Algorithmically the checks are `O(t^3)`-ish rather than the `O(t^5)` a literal
transcription costs; `mds_security.zig` documents the two equivalences that buy
that and the tests that hold them. Doing the derivation at
**comptime** instead was implemented and measured first: the Zig interpreter
costs roughly 18 µs per LFSR clock, which is about 5 s for `t = 3` alone and
~200 s for the full sweep. That is why the tables live in an instance rather
than in a `const`. `init()` is still an ordinary function, so
`const P = comptime Perm(3).init();` works for a caller who prefers to pay
compile time.
