# `keycodec` — changelog

Newest first. See the root [`CHANGELOG.md`](../../CHANGELOG.md) for which
release tag each entry shipped in, and `CONVENTIONS.md` §8 for the policy.

## Unreleased

- **2026-11-20** — **Behaviour change:** an encrypted traditional PEM is written with `DEK-Info` second, after `Proc-Type`, as RFC 1421 §4.6.1 orders them (OpenSSL writes the same order); readers that accepted the old order still accept the new one.
- **2026-11-08** — **NO CONSUMER-VISIBLE CHANGE:** `pem`'s private `eqMask` is `b64ct.eqMask`.
- **2026-11-07** — **Fixed:** `pbes2.decrypt` and `pbes2.encrypt` (public through `keycodec.pbes2`) now burn the dead stack themselves (`burn.pbes2_burn`), as the root entry points already did; a direct call left ~1.9 KiB of KDF/HMAC/AES state below the caller. The stack probe calls both directly.
- **2026-11-07** — **Review fixes:** `parseEncryptedPrivateKeyPem` answers `UnsupportedEncryption` (not `NotEncrypted`) for an OpenSSL legacy `Proc-Type: 4,ENCRYPTED` block under the plain `RSA PRIVATE KEY` / `EC PRIVATE KEY` / `PRIVATE KEY` label; `pem.encodeWithHeaders` refuses control bytes other than a tab in a header value (NUL, ESC, DEL); tests now assert the decrypt-side wiping (`out`, `scrypt_work`, the in-place PEM region); SPEC states the timing limit of the single error.
- **2026-11-07** — **Encrypted PKCS#8 (PBES2) read and written, PEM headers on encode** (the two gaps of the 2026-11-05 survey; Scope `core` → `parity`). New: `parseEncryptedPkcs8`, `parseEncryptedPrivateKeyPem`, `decryptPkcs8`, `parseEncryptedInfo`, `encryptPkcs8`, `writeEncryptedPrivateKeyPem` (`ENCRYPTED PRIVATE KEY`: PBKDF2 with HMAC-SHA-1/224/256/384/512 or scrypt, AES-128/192/256-CBC; no allocation, scrypt memory is the caller's `DecryptOptions.scrypt_work`; hostile iteration counts, scrypt cost and memory are `KdfParamsTooLarge`; a wrong password and bad padding are one error), `pem.encodeWithHeaders`, `writePrivateKeyPemWithHeaders`, `pem.Block.header` / `headerIterator`. Output is `openssl pkcs8 -topk8`'s byte for byte for the same salt and IV; 15 OpenSSL 3.5.5 fixtures (`src/vectors_enc.zig`, `tools/vectors.py --encrypted`). New dependencies `aescbc` and `aes192`. No existing error set changed. `rsa.fromPkcs8Encrypted` now decrypts through `pbes2` (same behaviour).
- **2026-11-06** — **Tests:** every OpenSSL ML-KEM key (seed, expanded, both; 512/768/1024) loads into the zig-libs `mlkem` module with OpenSSL's public key, and an `mlkem` key written through keycodec is OpenSSL's bytes (`src/mlkem_test.zig`, test dependency `mlkem`). tlsserver and acme now read keys through keycodec.
- **2026-11-05** — Independent review fixes: a PKCS#8 v2 RSA public key is checked (and written back); a one-line PEM followed by a comment with a `:` reads; PKCS#1 is strict by version (v0: eight INTEGERs, v1: non-empty `otherPrimeInfos`), no INTEGER is empty, PKCS#8 attributes must be Attribute SEQUENCEs; a PKCS#8 EC key without a curve in its AlgorithmIdentifier takes the inner `[0]` (Go's fallback); the PKCS#1 writer checks its fields; a failed write zeroes what it wrote; a stray `-----BEGIN ` in comment text is skipped; the writer's stack burn reaches past its 16 KiB buffer. New `writeRsaPublicKeyPem` (PKCS#1 `RSA PUBLIC KEY`).
- **2026-11-05** — New module: PKCS#8, SEC1, PKCS#1 and SPKI key encodings with constant-time PEM, for EC (P-256/384/521, secp256k1), Ed25519/Ed448, X25519/X448, RSA/RSASSA-PSS, ML-DSA and ML-KEM; type-agnostic (a key is its algorithm plus slices of the caller's DER), so `jwt`, `acme`, `tlsserver` and `mlkem` can share one reader instead of carrying four. Anchored on 33 OpenSSL 3.5.5 keys read into the parts OpenSSL prints and written back byte for byte.
