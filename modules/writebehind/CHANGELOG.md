## Unreleased

- **2026-11-19** — **NO CONSUMER-VISIBLE CHANGE (tests and docs):** delta mutation of the wbmut-1/wbmut-2 fixes. 36 mutants (30 over the changed source and the 6 left open by the 2026-11-18 run), 25 of the 30 killed and 5 equivalent; the 6 old ones are equivalent (the `unflushed` counter is exact: `readyCount()` at reopen already counts records whose backoff is still running). Three tests added: a record in a WAL-persisted backoff (WALs written before this release) is counted at reopen and lands through `recover`, the synchronous path or a pool flush; back-pressure honours a key's retry backoff; the synchronous path keeps per-key retry deadlines exact. Card: mutation 2026-11-19 (275/310, 35 eq), cumulative.
- **2026-11-19** — **API change / Behaviour change / Fix: `flushAll` waits until every pending write has landed or definitively failed, bounded by a deadline; a retry backoff no longer breaks last-writer-wins.** API change: `flushAll` and `sync` return `FlushError!void`; the new `error.FlushIncomplete` comes after the new `Options.flush_timeout_ns` (default 120 s, Kafka's `delivery.timeout.ms`; 0 = one synchronous pass, `maxInt` = no limit), with the remaining records still in the WAL. Callers add `try`. Behaviour change: `flushAll` used to return as soon as nothing was visible, i.e. during a `retry_backoff_ns` wait or after one rejected synchronous write, with records pending; it now waits them out, and a rejected synchronous write is retried after the other records. `deinit` blocks up to `flush_timeout_ns` against a sink that keeps refusing (it blocked forever before; `deinitNoFlush` exits at once). Behaviour change: `retry_backoff_ns` is an in-memory per-key wait on `wal_mono_clock`, no longer a WAL backoff, so it is not persisted and a restart retries at once. Fix: a WAL backoff took the failed record out of its key's FIFO, so a newer write to the key reached the sink first and the retried older value then overwrote it (in-process and after a restart). Fix: a failed key stays registered, so `drain()` alone retries it after the backoff (it was reconciled clean and left to `flushAll`). Fix: the synchronous flush path and `recover()` count a dead-lettered record (`poisonedCount`) instead of leaving it pending forever. Audit finding wbmut-1; SPEC "Sink write failure".
- **2026-11-19** — **Fix: `deinitNoFlush` no longer leaks the tasks of the flush jobs it drops, nor submits to a freed pool.** `shutdownNow` discards queued jobs unrun; their `FlushTask`, key and value (three allocations each) were never freed. The in-flight set now records each key's task and `deinitNoFlush` frees what is still listed after the harvest. The harvest itself ran after `pool.deinit`, so a completed flush that advanced its key to a next record called `pool.submit` on freed memory; it now runs before, where a stopped pool refuses the submit and the record stays in the WAL. Audit finding wbmut-2; the test that drops queued jobs runs on the leak-checking allocator.
- **2026-11-18** — **NO CONSUMER-VISIBLE CHANGE (tests and docs):** whole-module mutation audit of `src/root.zig`, 280 mutants, 250 killed, 24 equivalent or unobservable and 6 open (card replaced: it was a cumulative 45/52 over a 32-mutant run of unknown base). 29 tests added (WAL refusal errors, every flush path acking its record, lease lifetime, injected clocks, allocation failures in `startFlush`, a refused pool submit, `flushOneSync` and `deinitNoFlush` behaviour) and the test `FailingSink` no longer leaves a freed key in its map on an overwrite. Two defects recorded, not fixed: `flushAll` returns with records pending when `retry_backoff_ns > 0` or a synchronous flush is rejected, and `deinitNoFlush` leaks the tasks of queued jobs it drops (SPEC "Findings of the audit").
- **2026-11-18** — **API addition:** back-pressure for `put`/`del`. `Options.max_unflushed` (entries, default 0 = unbounded, so existing users see no change) is a high-water mark on `pendingCount()`; at the mark the writer drives the flush and waits up to `Options.put_block_ns` (default 60 s, Kafka's `max.block.ms`; 0 = no wait), then fails with the new `PutError.Backpressure`, having written nothing. A caller that switches on `PutError` exhaustively must handle the new member. Ehcache `queueSize` / Kafka `buffer.memory`+`max.block.ms` semantics, see SPEC "Back-pressure".
- **2026-10-24** — **NO CONSUMER-VISIBLE CHANGE:** the `strRepeat` helper (the Zig 0.17 stand-in for `**`) builds its string with one `@splat` + `@bitCast` instead of a comptime loop, which Sema evaluated in O(n²) (http's test binary: 323 s → 13 s). Same bytes, faster compile.

- **2026-10-05** — **Fix: `flushAll` could stop with a record still pending.** On its synchronous
  backstop path (a reopened WAL nobody `recover()`ed) `flushOneSync` read the key through a lease
  `ack` had already freed, then leased that key's next record and dropped the lease, hiding it
  for the 60 s visibility timeout. It now copies the key first and hands the next record to the
  pool. Mutation run: 26 of 32 killed, 4 equivalent, 1 exposed this bug, 1 not killable by a
  value test (the use-after-free itself); 6 tests added (the regression, `put` after `del`, read-through failure,
  `recover` of a delete, `drain()` over two records of one key, one sink call in flight per key).
- **2026-10-01** — **Fix: `KvtreeSink` no longer spins on its lock under a fiber/evented `Io`.**
  It held a spinlock across `kvtree` writes (an fsync each); concurrent flush tasks on one
  thread spun on it forever while the holder was suspended. It now uses `kvtree.Lock`
  (`std.Io.Mutex` when the `Db`'s storage has an `Io`). Found by the spinlock audit that
  followed the simio kv pilot.
- **2026-08-06** — Security audit: five findings fixed (part of the collection-wide
  audit; the root changelog records no further detail than this). Modeled on Caffeine
  `writeBehind` / a DB buffer pool (design reference, not a test anchor).
- **2026-07-22** — New module: crash-safe write-behind cache coordinator.
