## What this module is, and what it is not

The AES-192 block cipher, as the third member of std's `Aes128`/`Aes256` family. Purpose and
usage: [README.md](README.md).

**Not here:** any mode of operation (CBC, CTR beyond what `std.crypto.core.modes.ctr` already
gives, GCM, KW, …). Those live in `aescbc`, `aesgcm`, `aeskw`, `jwe`, `xmlenc`, `ssh`; giving
them a 192-bit key is phase 2 (*Open*). No own round implementation and no own S-box either —
deliberately (*Design*).

## Algorithm

FIPS-197 (2001; 2023 update `-upd1`), Nk = 6, Nr = 12.

- **Key expansion** — §5.2 Algorithm 2 (`expand`, `root.zig`): w[0..5] = the key, then for
  i = 6..51, `temp = w[i-1]`, every sixth word `SubWord(RotWord(temp)) ⊕ Rcon[i/6]` with
  Rcon = 01, 02, 04, …, 80, and `w[i] = w[i-6] ⊕ temp`. Round key r = w[4r..4r+3], in
  std's byte order (`Block.fromBytes` of the 16 bytes). Every branch is on the loop index.
- **SubWord** — std's last-round primitive on a state of four identical columns:
  `encryptLast(w‖w‖w‖w, 0)` = ShiftRows(SubBytes(·)) ⊕ 0, and ShiftRows is the identity when
  each row holds one repeated byte, so the first column is SubWord(w). This keeps the only
  secret-indexed operation of the expansion inside the backend std already chose.
- **Cipher** — §5.1: AddRoundKey(rk0), 11 × `Block.encrypt`, `Block.encryptLast(rk12)`.
- **Decryption** — the equivalent inverse cipher, §5.3.5 (as std's `AesDecryptCtx`): round
  keys reversed, InvMixColumns on rk1..rk11, then `Block.decrypt` × 11 and `decryptLast`.
  InvMixColumns is composed as `decrypt(encryptLast(x, 0), 0)` rather than
  `Block.invMixColumns`, because on std 0.16's software backend the latter branches on the
  key byte (`soft.zig:805`, inside its GF(2^8) `mul`) — measured: 872 memcheck contexts in the
  `dec` harness before the change, 0 branches after.
- **Wide calls** — an unrolled loop of one-block rounds (`roundWide`), which is what std's
  `Block.parallel.*Wide` is on AES-NI/ARMv8. Not called through std because in Zig 0.16.0 the
  software backend's `parallel.*Wide` does not compile (`var i = 0;`, `soft.zig:315`).

## Design & invariants

- **Shape = std's.** `Aes192` has `key_bits`, `rounds`, `block`, `initEnc`, `initDec`; the
  contexts have `block`, `block_length`, `key_schedule.round_keys`, and the same method set and
  signatures as `AesEncryptCtx(Aes)` / `AesDecryptCtx(Aes)`. A mode generic over std's types
  needs no change beyond accepting the third type (test: SP 800-38A CTR through
  `std.crypto.core.modes.ctr`). std's own `AesEncryptCtx` cannot be reused: it asserts
  `key_bits == 128 or 256`, and its `KeySchedule` is private.
- **Backend = std's, at compile time**, by the same switch as for `Aes128`/`Aes256`
  (`has_hardware_support` re-exported).
- **Dead stack** (`CONVENTIONS.md` §2.1.1): `init`/`initInto` of both contexts (and the
  `Aes192.init*` forwards) run under a 512-byte burn (the body dirties ≤ 256 B in ReleaseFast;
  512 is the probe's minimum zero run; 4 KiB until 2026-10-11, when it was half of `init`'s time); the by-value `initEnc`/`initDec`/`init`
  are the std-shaped surface, with `*Into` twins. Per-block calls do not burn (§2.1 Z3: the
  burn belongs to the mode's entry point that owns key and message). `stackprobe_test.zig`
  (ReleaseFast) holds the burn deep enough.
- **Zeroization:** a context is caller-owned storage (§2.1 Z2): `wipe()` on each, documented,
  tested (`wipe zeroes the round keys`). The 52-word expansion buffer is Z3 (a key schedule),
  covered by the burn.

## Constant-time contract

Secret: the key (hence every round key) and the data blocks.

- **AES-NI / ARMv8 Crypto backends:** the key expansion, the schedule inversion and every
  round are fixed instruction sequences with no secret-dependent branch or address.
  Machine-checked on AES-NI by `scripts/checks/ctgrind.sh aes192` (`-Dcpu=skylake`, the
  script's pinned CPU): rows `enc` and `dec` in `ctgrind-expected.tsv`, **0 in-file**; all
  contexts are the harness's printed results (witness). ARMv8 is not measured under valgrind
  here (no arm64 host); the claim there rests on the code being std's `aese`/`aesd` sequences.
- **Software backend** (`has_hardware_support == false`): exactly std's `Aes128`/`Aes256`
  posture, no worse. std's tables are read with cache-line-granular masking
  (`std.options.side_channels_mitigations`, default `.medium`), which is a mitigation, not
  constant time: memcheck sees the secret-indexed loads. Measured 2026-10-10,
  `CTGRIND_CPU=x86_64 scripts/checks/ctgrind.sh --stacks aes192` (not a pinned row — the
  script pins one CPU for all modules): `enc` 356 in-file, `dec` 349 in-file, **every one a
  "Use of uninitialised value" (a load address) at `soft.zig:127-134, 838-840, 878-880`**,
  zero conditional jumps. A consumer that needs constant time on a CPU without AES
  instructions needs a bitsliced AES, which neither std nor this module provides.

## Limits and refusals

Key exactly 24 bytes (by type). Block exactly 16 bytes (by type). No runtime errors exist.

## Performance

Measured 2026-10-11 against OpenSSL 3.5.5 (system `libcrypto.so.3`, EVP AES-192: the AES-NI
`aesni_*` kernels). Host: Intel Core i7-7920HQ (Kaby Lake; AES-NI, no VAES), Linux 7.0, Zig
0.16.0 ReleaseFast against `zig cc -O3 -march=native`, load average ~2.7 (other sessions).

Method: `zig build bench-aes192` (`tools/bench.zig` driving `tools/c_bench/foreign_bench.c`,
the shared alternating driver of the crypto benches; ratio = ours/theirs by user-mode cycles,
each side's best of `BENCH_ROUNDS=5`). Before timing, OpenSSL's ECB, CBC and CTR outputs of the
16 KiB message must equal ours byte for byte, and our ECB decryption must invert it.

| workload | what | ours ns/op | ref ns/op | ours/ref |
|---|---|---:|---:|---:|
| `ecb_enc_16384` | `encryptWide` at `optimal_parallel_blocks` vs EVP ECB | 3460 | 3506 | 0.997 |
| `ecb_dec_16384` | `decryptWide` vs EVP ECB | 3536 | 3451 | 1.013 |
| `cbc_enc_16384` | chained `encrypt` (latency) vs EVP CBC | 14533 | 14581 | 1.004 |
| `ctr_16384` | `std.crypto.core.modes.ctr` vs EVP CTR | 3474 | 3614 | 0.965 |
| `key_enc` | `Aes192EncryptCtx.init` (burn included) vs `EVP_EncryptInit_ex` with the key | 69 | 86 | 0.805 |
| `key_dec` | `Aes192DecryptCtx.init` vs `EVP_DecryptInit_ex` with the key | 69 | 93 | 0.741 |

A first run (before the key-setup change) agreed on the bulk rows (0.96–1.01×).

**Reading.** The rounds are the same AES-NI instructions on both sides, so bulk work meets at
1.00× ± 1.5 %. Key setup was 1.65–1.81× before 2026-10-11: half of it a 4 KiB dead-stack burn
for a body that dirties 256 B, half the expansion compiled to byte operations from `[4]u8`
words; with a 512-byte burn and `u32` words it is 0.74–0.81×. Grade: worst row 1.01× (within
`p2_ref_tolerance`), fastest in the field not measured, so P2.

## What is deliberately not done

- **An own software AES** (bitsliced or otherwise): not now. The point of the module is to add
  only what std lacks; a constant-time software path is a std gap for all three key sizes,
  not an AES-192 one.
- **aeskeygenassist-based expansion on AES-NI:** not done. The generic expansion is the same
  code on every backend and runs once per key; with word-wide XORs it is already 0.74–0.81×
  OpenSSL's EVP key setup (*Performance*), so a second, x86-only path buys nothing a user sees.

## Open

- **Phase 2:** done — 192-bit keys in `aescbc`, `aeskw` (A192KW), `aesgcm`, `jwe`
  (A192KW/A192GCM/A192CBC-HS384), `xmlenc` (aes192-cbc, kw-aes192), `ssh` (`aes192-ctr`).
- **Performance P2 → P1: measure the fastest in the field** *(bench 2026-10-11)*: P1 needs
  `fastest ≤ 1.25×` and only OpenSSL is measured. Candidates: aws-lc / BoringSSL, Go
  `crypto/aes` (as an `alt` side in `tools/bench.zig`).
- **ARMv8 backend under ctgrind:** not measured (no arm64 valgrind host); tested only for
  correctness under qemu (`-Dtarget=aarch64-linux-musl -Dcpu=cortex_a72 -fqemu`).
