# x509

X.509 certificate CHAIN / path validation (RFC 5280 §6) — the multi-certificate
trust verifier this collection lacks. `std.crypto.Certificate` parses one
certificate and verifies one link against one candidate issuer; the `rsa`
module only self-signs a single certificate. Neither builds or validates a
whole path against a trust store. Consumers: mutual-TLS client-certificate
authentication on a TLS-terminated server, and OPC-UA trust-list validation.

**Status: implemented.** Full RFC 5280 §6 certification-path validation:
DER parsing for the extension fields `std.crypto.Certificate` omits
(`basicConstraints`, `keyUsage`, `extKeyUsage`, `subjectKeyIdentifier`,
`authorityKeyIdentifier`, `nameConstraints` — see `extensions.zig`), plus the
path-building/policy decision layer (`chain.zig`): RFC 4158-style path
building with backtracking over multiple same-subject-DN candidates,
per-link signature verification (RSA PKCS1v15, RSASSA-PSS, ECDSA P-256/P-384,
Ed25519), basicConstraints/keyUsage CA-signer enforcement,
pathLenConstraint bookkeeping (self-issued-certificate exception included),
accumulated nameConstraints, extended-key-usage chaining, and hostname
matching. `zig build test-x509` (40 tests) cross-checks real
root/intermediate/leaf hierarchies generated by OpenSSL 3.5 — one hierarchy
per signature algorithm plus dedicated rejection-case hierarchies — see
`chain_test.zig`. Out of scope, by design: CRL/OCSP revocation and
certificate-policy processing (see SPEC.md).

```zig
const x509 = @import("x509");

// Extension parsing.
const ext_slice = (try x509.extensions.findExtensions(cert)).?;
var it = x509.extensions.iterate(ext_slice, cert);
while (try it.next()) |entry| {
    if (entry.id == .basic_constraints) {
        const bc = try x509.extensions.parseBasicConstraints(entry.value);
        // bc.is_ca, bc.path_len_constraint
    }
}

// Full RFC 5280 §6 path validation.
const verified = try x509.verifyChain(gpa, chain_der, trust_anchors_der, .{
    .now_sec = now,
    .expected_host = "api.example.com",
    .required_eku = .server_auth,
});
```

- **Model after:** RFC 5280 (X.509 v3 / PKIX Certificate and CRL Profile);
  built directly on `std.crypto.Certificate` (MIT, part of Zig std) for DER
  primitives and single-link parse/verify — this module adds path
  building + §6 policy on top, not a replacement parser.
- **Platform:** any. **Role:** util (pure verification logic, no I/O of its
  own). **Concurrency:** reentrant — every function is value-in/value-out,
  no shared/global state.
- **Deps:** `rsa` (for `rsa.PublicKey`/`rsa.verifyPss` — the RSASSA-PSS
  certificate-link gap `std.crypto.Certificate` cannot handle at all, since
  it can't even parse a PSS-signed certificate).

## Recon: what `std.crypto.Certificate` already gives us

See `src/root.zig`'s module doc comment for the full recon; summary:

- Real single-certificate DER parse (`Certificate.parse` → `Parsed`):
  version, issuer/subject DN bytes + commonName, validity window,
  signature algorithm, public-key algorithm, subjectAltName. Does **not**
  expose basicConstraints/keyUsage/extKeyUsage/subjectKeyIdentifier/
  authorityKeyIdentifier/nameConstraints values at all (the OIDs are
  *recognized* but never extracted).
- Real single-link verify (`Parsed.verify`): issuer/subject name match +
  validity window + signature, for RSA PKCS1v15, ECDSA P-256/P-384, and
  Ed25519. **No RSA-PSS support** — `Certificate.parse` itself rejects a
  PSS-signed certificate (unrecognized signature-algorithm OID).
- **No multi-certificate path building or RFC 5280 §6 policy anywhere in
  std.** `Certificate.Bundle` does a single hashmap lookup for one issuer
  candidate by subject DN (no multi-candidate handling); `Certificate.Chain`
  is a Windows-only shim over `CertGetCertificateChain` (not a portable
  algorithm to build on).

## `x509.extensions` — real, tested

`findExtensions`/`iterate` locate and walk a certificate's extension block
(std doesn't expose this at all beyond internally, for `subjectAltName`
only). Per-extension parsers: `parseBasicConstraints`, `parseKeyUsage`,
`parseExtKeyUsage`/`hasPurpose`, `parseSubjectKeyIdentifier`,
`parseAuthorityKeyIdentifier` (`keyIdentifier [0]` form only),
`parseNameConstraints`/`subtreeIterator`. Cross-validated against real
certificates from `rsa.selfSignedCert` plus hand-built DER fixtures for
shapes that generator doesn't emit (pathLenConstraint, extKeyUsage,
authorityKeyIdentifier, nameConstraints).

## `x509.chain` — implemented

`verifyChain(gpa, chain, trust_anchors, opts)` is the single entry point;
`Options`/`VerifiedChain`/`VerifyChainError` are fully typed. It composes
five separable, individually-tested sub-algorithms — `buildPath` (RFC
4158-style path building with backtracking over multiple same-subject-DN
candidates), `checkNameConstraints` (dNSName/directoryName/iPAddress),
`checkPathLength` (pathLenConstraint with the self-issued exception),
`checkExtendedKeyUsage`, and `verifyPssLink` (RSASSA-PSS certificate-link
verification, RFC 4055, applying its DEFAULT parameters exactly) — see each
one's doc comment in `src/chain.zig`. Every DER offset either file computes
goes through `extensions.parseElement`, a bounds-safe wrapper that turns a
malformed length field into a typed error instead of an out-of-bounds panic
(see `src/root.zig`'s doc comment).

## `x509.safe` — certificate-DER safety guard

The canonical guard in front of `std.crypto.Certificate.parse`, whose
unchecked DER reader **panics in Debug and reads out of bounds / segfaults in
ReleaseFast** on a malformed, attacker-supplied certificate (verified on Zig
0.16.0). `safe.validate` / `safe.validateCertificate` are a recursive-descent
DER well-formedness validator (its own bounds-checked decoder — it does not
trust std's reader) returning a typed `safe.Error`. `safe.safeCertificate(der,
scratch)` validates, then returns a zero-padded `std.crypto.Certificate` that
is safe to `parse` in every optimisation mode — the padding is required
because well-formedness alone does not make std's parse total (`SPEC.md`
gives the proof). This is the shared helper the `iec62351` and `opcua`
modules route through instead of each carrying its own copy.

```zig
var scratch: [x509.safe.max_certificate_len + x509.safe.parse_slack]u8 = undefined;
const cert = try x509.safe.safeCertificate(peer_cert_der, &scratch);
const parsed = try cert.parse(); // total: a hostile cert is a typed error, never a crash
```

## `x509.spkiOf` — name a certificate's public key, safely

When all you need from an untrusted certificate is *which key it names* — a
Holder-of-Key subject confirmation, a key-pinning check, a
certificate ↔ bare-public-key comparison — `x509.spkiOf` gives you its
`SubjectPublicKeyInfo` without ever going through
`std.crypto.Certificate.parse`. It runs `safe.validateCertificate` first, then
walks the `TBSCertificate` fields with `safe.zig`'s own bounds-checked header
decoder; no dates, extensions or signature bytes are decoded at all. It works
on certificates std cannot parse (RSASSA-PSS-signed ones), and every failure is
a typed `x509.SpkiError`.

```zig
const spki = try x509.spkiOf(peer_cert_der);       // every field borrows peer_cert_der
if (spki.algorithmIs(&x509.safe.oid_rsa_encryption)) {
    const pk = try rsa.PublicKey.fromDer(spki.der); // spki.der = the whole SPKI TLV
} else if (spki.algorithmIs(&x509.safe.oid_ec_public_key)) {
    const curve = spki.namedCurveOid() orelse return error.NoNamedCurve;
    if (std.mem.eql(u8, curve, &x509.safe.oid_prime256v1)) {
        const pk = try EcdsaP256Sha256.PublicKey.fromSec1(spki.key_bits);
    }
}
```

`spki.der` / `.algorithm_oid` / `.parameters` / `.key_bits` are **sub-slices of
the caller's buffer** — nothing is copied or allocated, so the whole `Spki` is
valid exactly as long as `peer_cert_der` is. This is a field accessor, not a
verifier: it proves the bytes are the certificate's SubjectPublicKeyInfo and
nothing about the certificate's signature, validity or issuer — use
`verifyChain` for that.

## Provenance

Clean-room implementation from RFC 5280 (X.509 v3 / PKIX Certificate and CRL
Profile), RFC 4055 (RSASSA-PSS in X.509), and RFC 6125 (hostname matching) —
public IETF specifications, not copyrightable works (see `CONVENTIONS.md` §5
/ `NOTICE` policy). Built directly on Zig std's `std.crypto.Certificate`
(MIT) and this repo's own `rsa` module (RFC 8017). See `/NOTICE` for the
full statement.
